# Immediate IPv4-first preference

`src/main/network-preferences.js` exports `applyNetworkPreferences(settings)` and an injectable `createNetworkPreferences({dnsModule,netModule})`. Setting `preferIPv4` is boolean; absent defaults true. Apply at main-process startup and whenever preferences change. Enabled sets Node's DNS default result order to `ipv4first`; disabled sets it to `verbatim` (the OS resolver's order). Both modes enable Node socket family autoselection so unreachable first-family addresses can fall through to the other family. IPv6 remains usable. Nothing forces family4, changes system DNS, disables IPv6, replaces proxy settings or relaxes TLS/certificate checks.

The [Node DNS API](https://nodejs.org/api/dns.html#dnssetdefaultresultorderorder) changes defaults for subsequent dns.lookup and promises.lookup calls. [Node socket family autoselection](https://nodejs.org/download/release/v24.21.0/docs/api/net.html#netsetdefaultautoselectfamilyvalue) supplies fallback. Applying this function changes those defaults synchronously without restart; existing requests, connected sockets and pooled keep-alive connections are not interrupted or re-resolved. Worker threads have separate DNS defaults and would need this function applied within them if future network code uses workers. Explicit per-request lookup/family settings can override defaults.

Current Scribble cloud-speech, cloud-ai and model-download modules use Node global fetch; new connections that use Node's default resolver inherit this preference. Chromium renderer requests and Electron net.fetch use Chromium networking, so this function intentionally returns `chromiumControlled:false` and does not claim to govern those requests. Do not change secure DNS or inject Chromium certificate/proxy overrides to imitate this toggle.

Return fields: `preferIPv4`, `dnsOrder`, `autoSelectFamily`, `scope:'node-new-connections'`, `chromiumControlled:false`. Missing DNS setter support is an explicit runtime error. A runtime without family-autoselection setter reports null; the packaged current Node runtime should support it. No network calls are made by applying settings.

Four tests passed on Node24.21.0: injected true/false transitions and invalid input, real DNS defaults/promises.lookup localhost address order, a real TCP connection falling from refused IPv4 loopback to a working IPv6 loopback server, and unsupported API handling. IPv6 fallback test was executed successfully, not skipped. No external connections, credentials, GUI changes or provider charges were involved. Electron packaged-main execution remains a separate root verification step.
